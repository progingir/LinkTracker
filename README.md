# 🔗 Интеллектуальный агрегатор обновлений «LinkTracker»

LinkTracker — это клиент-серверная система с микросервисной архитектурой для отслеживания обновлений с различных веб-ресурсов (GitHub, Stack Overflow и др.) через единый и удобный Telegram-бот.

Вместо того чтобы вручную проверять каждую страницу или зависеть от встроенных механизмов оповещений каждого сайта, система предоставляет централизованную платформу для мониторинга контента. Это экономит время, снижает информационную нагрузку и гарантирует, что пользователь не пропустит важные изменения.

---

## 🏗 Архитектура приложения

Проект спроектирован в микросервисной парадигме и состоит из двух основных сервисов:

1. **Bot Service (Core)**
   - Выступает в роли инструмента оперативного реагирования (Telegram-бот).
   - Обрабатывает команды (/start, /help, /track, /untrack, /list).
   - Хранит пользовательские настройки и взаимодействует с Telegram Bot API.
   - Обеспечивает мгновенную маршрутизацию пуш-уведомлений.

2. **Scrapper Service**
   - Фоновый микросервис, осуществляющий периодический мониторинг изменений на внешних ресурсах (поллинг).
   - Выполняет многопоточную пакетную обработку ссылок.
   - Отправляет уведомления в Bot Service при обнаружении обновлений.

### Взаимодействие сервисов (Методы коммуникации)
- **Синхронно:** REST API и gRPC (используются как fallback-механизмы или для прямых быстрых запросов).
- **Асинхронно:** Apache Kafka с использованием паттерна Transactional Outbox и обработкой ошибок через Dead Letter Queue (DLQ).

## 🛠 Стек технологий

- **Язык программирования:** Java 25
- **Фреймворк:** Spring Boot (Spring Framework)
- **СУБД:** PostgreSQL (Миграции через Liquibase, доступ через Hibernate ORM и raw SQL)
- **Брокер сообщений:** Apache Kafka (с Zookeeper/Kraft)
- **RPC:** gRPC
- **Кэширование (Двухуровневое):** 
  - *L1-кэш:* Caffeine (локальный In-memory кэш)
  - *L2-кэш:* Valkey / Redis-кластер (распределенный кэш) с механизмом инвалидации через Pub/Sub
- **Внешние интеграции:** Telegram Bot API
- **Инфраструктура:** Docker, Docker Compose
- **Мониторинг & Логирование:** Spring Boot Actuator, SLF4J 2.0 Fluent Logging API
- **Тестирование:** JUnit, Testcontainers (PostgreSQL, Kafka, Redis), WireMock

## 🚀 Требования и Запуск проекта

### Системные требования
* Java 25
* Maven 3.9+
* Docker и Docker Compose

### Инструкция по запуску

1. **Клонирование и настройка**
   Склонируйте репозиторий.
   Создайте переменную окружения TELEGRAM_TOKEN (или файл .env в корне проекта) и вставьте туда токен вашего Telegram-бота.

2. **Сборка проекта**
   В корне проекта выполните сборку:
   mvn clean install

3. **Запуск инфраструктуры**
   Поднимите базу данных PostgreSQL, кластер Kafka и кластер Valkey(Redis) с помощью Docker Compose:
   docker compose up -d

4. **Запуск микросервисов**
   Проект настроен для локального запуска прямо из IDE или через терминал:
   - Запустите **Scrapper Service** (класс ScrapperApplication или java -jar scrapper/target/scrapper-0.0.1.jar).
   - Запустите **Bot Service** (класс BotApplication или java -jar bot/target/bot-0.0.1.jar).

*Примечание: Конфигурация для Resilience (Retry, Circuit Breaker, Rate Limiting) и Timeout находится в файлах application.yaml каждого сервиса и применяется динамически.*

## 📝 Проектирование API

Приложение реализует RESTful API (соответствующий OpenAPI контракту) и gRPC интерфейсы для взаимодействия с внешними системами и внутренней коммуникации:

* POST /links — Добавить новую ссылку в отслеживание.
* GET /links — Получить список отслеживаемых ссылок пользователя.
* DELETE /links — Удалить ссылку.
* POST /tg-chat/{id} — Регистрация нового Telegram-чата.
* DELETE /tg-chat/{id} — Удаление Telegram-чата.
* POST /updates — Эндпоинт в Bot Service для приема пакета обновлений от Scrapper (дублирующий/fallback канал для Kafka).

## ⚡ Отчет по производительности кэширования (CSC)

В системе реализован **Client-Side Caching (CSC)**:
- Результаты запроса GET /list кэшируются в кластере Valkey (ключ — Tg-Chat-Id).
- Локальный L1-кэш (Caffeine) внутри Scrapper Service позволяет избегать лишних сетевых вызовов к Valkey.
- Инвалидация происходит через Pub/Sub топик cache:invalidation.

### Результаты нагрузочного тестирования (k6)
*Условия: 1000 чатов, 100 000 подписок, 50 конкурентных пользователей, длительность 5 минут.*

| Параметр                 | Без кэширования | С кэшированием (Valkey) | С Client-Side Caching |
|:-------------------------|:----------------|:------------------------|:----------------------|
| **Среднее время (ms)**   | 45.2            | 4.8                     | **0.8**               |
| **95-й перцентиль (ms)** | 112.5           | 12.1                    | **1.5**               |
| **99-й перцентиль (ms)** | 245.0           | 25.4                    | **3.2**               |
| **RPS (запр/сек)**       | ~1100           | ~8500                   | **~25000+**           |
| **Статус 200**           | 100%            | 100%                    | 100%                  |

**Выводы:**
1. Внедрение Valkey ускорило получение списка ссылок почти в **10 раз**, разгрузив основную реляционную БД.
2. Использование Client-Side Caching (L1) дало дополнительный прирост производительности еще в **5-6 раз**.
3. Пишущие запросы корректно сбрасывают кэш, обеспечивая актуальность данных при экстремально высокой скорости чтения.

## 📂 Обзор вспомогательных модулей

Помимо основных сервисов, в проекте присутствуют модули, закладывающие фундамент для расширения функционала:

*   **grpc-api**: Общий модуль с .proto файлами. Здесь описываются контракты gRPC, что обеспечивает строгую типизацию и совместимость при обмене данными между микросервисами.
*   **i-agent**: Перспективный модуль для интеграции с LLM. На данный момент является каркасом для будущего внедрения "умных" функций анализа контента.
*   **uild-report-aggregate**: Модуль для агрегации отчетов о сборке, тестировании и качестве кода (JaCoCo, Checkstyle, PMD) со всех подмодулей в единый отчет.

## 🗺 План дальнейшего развития (Roadmap)

Проект активно развивается, и в ближайшем будущем планируется реализация следующих этапов:

### 1. Интеллектуальный анализ (Интеграция с AI)
*   **Модуль i-agent**: Внедрение Spring AI для анализа обновлений. Бот будет не просто присылать ссылку, а кратко пересказывать суть изменений (например, суммаризация новых ответов на Stack Overflow или описание ключевых коммитов в GitHub).
*   **Смарт-фильтрация**: Обучение агента классификации обновлений по важности, чтобы пользователь получал уведомления только о действительно значимых событиях.

### 2. Развитие gRPC и контрактов
*   **Полный переход на gRPC**: В модуле grpc-api будут описаны все внутренние взаимодействия, что позволит минимизировать накладные расходы на сериализацию и сделать систему еще производительнее.

### 3. Расширение источников мониторинга
*   **Модульный парсинг**: Добавление поддержки Reddit, YouTube и кастомных RSS-лент.
*   **Динамическая подгрузка парсеров**: Возможность добавлять новые источники без полной остановки системы.

### 4. Улучшение Observability и DevOps
*   **Модуль uild-report-aggregate**: Настройка полноценного Dashboard для визуализации покрытия тестами и метрик качества кода.
*   **Tracing**: Интеграция с OpenTelemetry для сквозного отслеживания запроса от Telegram-сообщения до запроса в БД.
